     1→     1→# DOCUMENT 1 — SYSTEM & ARCHITECTURE SPECIFICATION
     2→     2→## AegisBank — Cloud-Native Digital Banking Platform (Student/Demo Build)
     3→     3→
     4→     4→> **Scope note (ARCHITECTURE DECISION #0):** The source report specifies Kubernetes + Kafka + full
     5→     5→> microservices with per-service databases. For a student/demo project this is massively over-engineered
     6→     6→> (cost, ops burden, deployment time all explode; VIT-level demo does not need multi-week K8s ops).
     7→     7→> We preserve every *logical* boundary the report defines (Auth/KYC, Account, Transaction, Payment,
     8→     8→> Fraud, Notification) as **separate backend modules inside one modular monolith**, communicating
     9→     9→> in-process via an internal event bus (simple pub/sub / outbox pattern), with **one PostgreSQL
    10→    10→> database using separate schemas per module** (not literally separate DBs) to keep data ownership
    11→    11→> boundaries clean without the operational cost of polyglot persistence. This is deployable on a single
    12→    12→> low-cost AWS compute unit. Document 3 also describes the scale-up path back to ECS+SQS/EventBridge or
    13→    13→> EKS+MSK if this were ever a real product. This decision is preserved throughout; do not reintroduce
    14→    14→> Kubernetes/Kafka without re-justifying cost.
    15→    15→

    18→    18→## 1. Project Overview
    19→    19→
    20→    20→**Problem:** Traditional monolithic core banking systems are hard to scale and risky to update.
    21→    21→
    22→    22→**Objective:** Build AegisBank, a system that logically decomposes banking into independent
    23→    23→capabilities (accounts, transactions, payments, auth/KYC, fraud detection, notifications) connected
    24→    24→via events rather than tight coupling, demonstrating cloud-native design principles at low cost.
    25→    25→
    26→    26→**Scope (demo-realistic):**
    27→    27→- User registration, login (JWT), basic KYC document upload + manual/simulated approval
    28→    28→- Account creation, balance view, statements
    29→    29→- Internal fund transfers between AegisBank accounts (Saga-style two-step balance update)
    30→    30→- Simulated external "payment rail" (mocked UPI/card top-up) decoupled via the event bus
    31→    31→- Rule-based fraud checks (velocity, large-amount, new-device) run asynchronously post-transaction
    32→    32→- Email/console notifications on transaction, fraud-flag, KYC-status-change events
    33→    33→- Admin view for fraud review
    34→    34→
    35→    35→**Out of scope (explicitly, to avoid overengineering):** real payment gateway integration, real SMS
    36→    36→gateway (mocked), multi-currency, regulatory reporting, high-availability multi-region, Kubernetes,
    37→    37→Kafka, distributed tracing infrastructure (basic structured logs + CloudWatch instead).
    38→    38→
    39→    39→**Users:** Customer, Admin/Fraud Analyst.
    40→    40→
    41→    41→**Major capabilities:** AuthN/KYC, Account mgmt, Transactions, Payments (mock), Fraud detection,
    42→    42→Notifications, Event bus (internal).

    75→    75→- Team is student-scale; must be buildable/deployable by one AI coding agent without a DevOps team.

    82→    82→  admin approval), not real identity verification.
    83→    83→- A3: Single currency (INR), single region deployment.
    84→    84→- A4: Fraud rules are simple threshold rules, not ML — explicitly per report's own permission to use
    85→    85→  deterministic logic where sufficient (Section 8 of the master prompt).

   146→   146→### 3.3 Request Flow (fund transfer)
   147→   147→
   148→   148→```mermaid
   149→   149→sequenceDiagram
   150→   150→    participant U as User
   151→   151→    participant GW as API Gateway Layer
   152→   152→    participant TXN as Transaction Module
   153→   153→    participant ACC as Account Module
   154→   154→    participant DB as Postgres
   155→   155→    participant BUS as Event Bus
   156→   156→    participant FRAUD as Fraud Module
   157→   157→    participant NOTIF as Notification Module
   158→   158→
   159→   159→    U->>GW: POST /api/v1/transactions (JWT)
   160→   160→    GW->>TXN: validated request
   161→   161→    TXN->>ACC: reserve debit (Saga step 1)
   162→   162→    ACC->>DB: check balance, lock row, debit
   163→   163→    TXN->>ACC: apply credit (Saga step 2)
   164→   164→    ACC->>DB: credit destination
   165→   165→    alt any step fails
   166→   166→        TXN->>ACC: compensating transaction (reverse debit)
   167→   167→    end
   168→   168→    TXN->>DB: insert transaction row (status=completed)
   169→   169→    TXN->>BUS: publish transaction.created
   170→   170→    BUS-->>FRAUD: transaction.created
   171→   171→    FRAUD->>DB: evaluate rules, write fraud_flag if needed
   172→   172→    FRAUD->>BUS: publish fraud.flagged (if any)
   173→   173→    BUS-->>NOTIF: transaction.created / fraud.flagged
   174→   174→    NOTIF->>U: email via SES
   175→   175→    TXN-->>U: 201 Created (transaction result)
   176→   176→```

   182→   182→    participant U as User
   183→   183→    participant GW as API Gateway Layer
   184→   184→    participant AUTH as Auth Module

   186→   186→

   220→   220→## 4. Technology Stack
   221→   221→
   222→   222→| Layer | Choice | Why required | Why selected | Alternatives considered | Cost impact | Complexity impact |
   223→   223→|---|---|---|---|---|---|---|
   224→   224→| Backend language/framework | Node.js + Express (TypeScript) | REST API, JWT, business logic | Fast to build, huge ecosystem, easy for AI coding agent to scaffold, cheap to run | Python/FastAPI (equally valid — pick one) | Low | Low |
   225→   225→| Database | PostgreSQL | Relational integrity for money/ledger data | ACID transactions essential for balances; JSONB for flexible KYC metadata | DynamoDB (poor fit for relational ledger + Saga joins) | Low (RDS free-tier eligible / small instance) | Low |
   226→   226→| Event bus | In-process pub/sub + Postgres outbox table | Report requires event-driven decoupling | Achieves decoupling/audit-log/replay semantics of Kafka without cluster cost | Kafka/MSK, SNS+SQS | None extra (reuses DB) / SNS+SQS ~$0-2/mo if chosen instead | Low vs. very high for Kafka |
   227→   227→| Frontend | React (Vite) | Web client per report | Simple SPA, deploys as static files to S3/CloudFront | Next.js (adds SSR complexity not needed) | Very low (S3+CloudFront) | Low |
   228→   228→| Auth | JWT (access+refresh), bcrypt | Report: Auth/KYC service issuing tokens | Stateless, no session store needed | AWS Cognito | Cognito free tier is fine too, but adds AWS-specific vendor coupling; JWT chosen for portability | Low either way |
   229→   229→| File storage (KYC docs) | Amazon S3 | Report: KYC document checks | Cheapest durable object storage | EFS | Pennies/month | Low |
   230→   230→| Email notifications | Amazon SES | Report: Notification Service | Cheapest transactional email on AWS | SNS (no email formatting), third-party (Sendgrid) | ~$0 for low volume (sandbox) | Low |
   231→   231→| Compute | ECS Fargate (1 small task) or single EC2 t3/t4g.micro | Report: containerised deployment | Fargate = no server mgmt, pay-per-use; EC2 = cheapest possible always-on option | EKS/Kubernetes (rejected: massive overkill/cost for this scale) | Fargate ~$8–15/mo min; EC2 t4g.micro ~$6–7/mo (or free-tier 12mo) | Fargate simpler ops; EC2 cheaper long-run |
   232→   232→| CI/CD | GitHub Actions | Report requires simple CI/CD | Free for public/small private repos, integrates with ECR/ECS | Jenkins, CodePipeline | Free tier sufficient | Low |
   233→   233→| IaC | AWS CDK (TypeScript) | Report requires IaC, avoid pure-console clickops | Same language as backend, good AI-agent authoring target | Terraform, SAM, CloudFormation raw | Free (pay only for resources) | Low-medium |

   237→   237→## 5. Application Components
   238→   238→
   239→   239→| Module | Responsibility | Inputs | Outputs | Dependencies | Interfaces | Failure behavior |
   240→   240→|---|---|---|---|---|---|---|
   241→   241→| API Gateway Layer | Routing, JWT verification, rate limiting, request logging | HTTP requests | Routed requests / 401/429 | Auth module (token verify) | Express middleware chain | Reject with 401/429/500; never crash whole process on one bad request |
   242→   242→| Auth/KYC | Register/login/refresh, KYC upload+status | Credentials, KYC files | JWT tokens, KYC status | Postgres, S3 | `/api/v1/auth/*`, `/api/v1/kyc/*` | Invalid creds → 401; on DB outage → 503 |
   243→   243→| Account | Account CRUD, balance queries, ledger system-of-record | Account ops | Balances, account records | Postgres | `/api/v1/accounts/*` | Insufficient funds → 422; concurrent-write handled via row locks |
   244→   244→| Transaction | Fund transfers, Saga orchestration | Transfer requests | Transaction records, events | Account module, Event Bus | `/api/v1/transactions/*` | On step failure → compensating reversal + `transaction.failed` event |
   245→   245→| Payment | Mock external top-up/withdrawal, async settlement | Payment requests | Payment records, events | Account module, Event Bus, mock external API | `/api/v1/payments/*` | Mock gateway timeout → retry x3, then `payment.failed` event |
   246→   246→| Fraud Detection | Rule evaluation on events | `transaction.created`, `payment.completed` | `fraud_flag` rows, `fraud.flagged` event | Event Bus, Postgres | Internal consumer (no public API except admin read) | Rule error logged, transaction NOT blocked (fraud is async/non-blocking per report) |
   247→   247→| Notification | Deliver alerts on events | Events | Emails (SES) | Event Bus, SES | Internal consumer | SES failure logged & retried; never blocks originating transaction |
   248→   248→| Event Bus (outbox) | Decouple producers/consumers, provide replayable log | Domain events | Delivered events to consumers | Postgres | `publishEvent()`, polling worker | Failed delivery retried with backoff; events never lost (persisted row) |

   344→   344→### 6.2 Table Detail
   345→   345→
   346→   346→**users** — Purpose: identity + KYC status.
   347→   347→`id UUID PK`, `email TEXT UNIQUE NOT NULL`, `password_hash TEXT NOT NULL`, `full_name TEXT NOT NULL`,
   348→   348→`role TEXT NOT NULL DEFAULT 'customer' CHECK (role IN ('customer','admin'))`,
   349→   349→`kyc_status TEXT NOT NULL DEFAULT 'pending' CHECK (kyc_status IN ('pending','approved','rejected'))`,
   350→   350→`created_at TIMESTAMPTZ NOT NULL DEFAULT now()`. Index: `email`.
   351→   351→
   352→   352→**kyc_documents** — Purpose: uploaded KYC docs + review state.
   353→   353→`id UUID PK`, `user_id UUID FK→users.id NOT NULL`, `doc_type TEXT NOT NULL`, `s3_key TEXT NOT NULL`,
   354→   354→`status TEXT NOT NULL DEFAULT 'pending'`, `submitted_at TIMESTAMPTZ DEFAULT now()`, `reviewed_at TIMESTAMPTZ`.
   355→   355→Index: `user_id`.
   356→   356→
   357→   357→**accounts** — Purpose: ledger system of record.
   358→   358→`id UUID PK`, `user_id UUID FK→users.id NOT NULL`, `account_number TEXT UNIQUE NOT NULL`,
   359→   359→`account_type TEXT NOT NULL DEFAULT 'savings'`, `balance NUMERIC(18,2) NOT NULL DEFAULT 0 CHECK (balance >= 0)`,
   360→   360→`status TEXT NOT NULL DEFAULT 'active'`, `created_at TIMESTAMPTZ DEFAULT now()`.
   361→   361→Indexes: `user_id`, `account_number`.
   362→   362→
   363→   363→**transactions** — Purpose: internal transfers (Saga-tracked).
   364→   364→`id UUID PK`, `source_account_id UUID FK→accounts.id NOT NULL`, `destination_account_id UUID FK→accounts.id NOT NULL`,
   365→   365→`amount NUMERIC(18,2) NOT NULL CHECK (amount > 0)`,
   366→   366→`status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','completed','failed','reversed'))`,
   367→   367→`saga_state TEXT NOT NULL DEFAULT 'started'`, `created_at TIMESTAMPTZ DEFAULT now()`.
   368→   368→Indexes: `source_account_id`, `destination_account_id`, `created_at`.
   369→   369→
   370→   370→**payments** — Purpose: external mock top-up/withdrawal.
   371→   371→`id UUID PK`, `account_id UUID FK→accounts.id NOT NULL`, `amount NUMERIC(18,2) NOT NULL CHECK (amount > 0)`,
   372→   372→`direction TEXT NOT NULL CHECK (direction IN ('credit','debit'))`, `provider_ref TEXT`,
   373→   373→`status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','completed','failed'))`,
   374→   374→`created_at TIMESTAMPTZ DEFAULT now()`. Index: `account_id`.
   375→   375→
   376→   376→**fraud_flags** — Purpose: async fraud evaluation output.
   377→   377→`id UUID PK`, `transaction_id UUID FK→transactions.id`, `payment_id UUID FK→payments.id`,
   378→   378→`severity TEXT NOT NULL CHECK (severity IN ('LOW','MEDIUM','HIGH'))`, `reason TEXT NOT NULL`,
   379→   379→`reviewed_status TEXT NOT NULL DEFAULT 'open' CHECK (reviewed_status IN ('open','reviewed','dismissed'))`,
   380→   380→`created_at TIMESTAMPTZ DEFAULT now()`. Index: `reviewed_status`.
   381→   381→Constraint: exactly one of `transaction_id`/`payment_id` set (`CHECK (num_nonnulls(transaction_id,payment_id)=1)`).
   382→   382→
   383→   383→**notifications** — Purpose: delivery log.
   384→   384→`id UUID PK`, `user_id UUID FK→users.id NOT NULL`, `channel TEXT NOT NULL DEFAULT 'email'`,
   385→   385→`event_type TEXT NOT NULL`, `status TEXT NOT NULL DEFAULT 'sent'`, `created_at TIMESTAMPTZ DEFAULT now()`.
   386→   386→
   387→   387→**event_outbox** — Purpose: internal event bus persistence/replay log.
   388→   388→`id UUID PK`, `event_type TEXT NOT NULL`, `payload JSONB NOT NULL`,
   389→   389→`status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','processed','failed'))`,
   390→   390→`attempts INT NOT NULL DEFAULT 0`, `created_at TIMESTAMPTZ DEFAULT now()`, `processed_at TIMESTAMPTZ`.

   466→   466→## 8. AI/ML Architecture
   467→   467→
   468→   468→**ARCHITECTURE DECISION:** No ML model or LLM is required. Fraud detection is implemented as
   469→   469→deterministic rule evaluation (velocity, amount-threshold, new-device/IP) triggered by the internal
   470→   470→event bus. This satisfies the report's own instruction ("if a simpler deterministic approach is
   471→   471→sufficient... state that"). No prompt pipeline, no model hosting, no inference cost.
   472→   472→
   473→   473→If the project is extended toward ML-based fraud scoring in future: input = transaction feature
   474→   474→vector (amount, time-of-day, account age, velocity count), output = risk score 0–1, candidate
   475→   475→approach = a small logistic-regression/gradient-boosted model trained offline and invoked via a
   476→   476→lightweight scikit-learn inference function — deliberately out of scope for this build.

   480→   480→## 9. Security Architecture
   481→   481→
   482→   482→- **Authentication:** JWT (HS256, short-lived 15 min access + 7 day refresh, refresh stored hashed).
   483→   483→- **Password handling:** bcrypt (cost factor 12), never logged.
   484→   484→- **Secrets:** AWS Secrets Manager / SSM Parameter Store (SecureString) for DB creds, JWT secret, SES config — never in repo or `.env` committed.
   485→   485→- **API security:** input validation on every endpoint (schema), rate limiting (e.g. 100 req/min/IP) at gateway layer, HTTPS-only (ALB/CloudFront + ACM cert, HTTP→HTTPS redirect).
   486→   486→- **Injection:** parameterized queries only (ORM/query builder — no string concatenation SQL).
   487→   487→- **XSS:** React auto-escapes; sanitize any HTML rendering; CSP header set.
   488→   488→- **CSRF:** not applicable to token-in-header API (no cookies used for auth); if cookies are later used, add CSRF tokens.
   489→   489→- **File upload security:** KYC uploads restricted to PDF/JPG/PNG, max 5MB, virus-scan optional (ClamAV out of scope for demo — document as open issue), stored in private S3 bucket, served via signed URLs only.
   490→   490→- **Prompt injection:** N/A (no LLM in this build).
   491→   491→- **Data privacy:** PII (email, KYC docs) access restricted to owner + admin role; do not log PII/PAN in plaintext logs; mask account numbers in logs (`****1234`).
   492→   492→- **Logging:** structured JSON logs to CloudWatch; no secrets/passwords/tokens logged.
   493→   493→- **IAM:** ECS task role scoped to only: read/write its S3 bucket, read Secrets Manager secrets it needs, write CloudWatch Logs. No `*` permissions.
   494→   494→- **Encryption:** RDS encryption-at-rest enabled, S3 bucket encryption (SSE-S3) enabled, TLS in transit everywhere.

   498→   498→## 10. Error Handling
   499→   499→
   500→   500→| Failure | Handling |
   501→   501→|---|---|
   502→   502→| Bad request body | 400 with field-level validation errors |
   503→   503→| Auth failure | 401, generic message (no user enumeration) |
   504→   504→| Authorization failure | 403 |
   505→   505→| Not found | 404 |
   506→   506→| Insufficient funds | 422 `INSUFFICIENT_FUNDS` |
   507→   507→| DB unavailable | 503, retry with backoff at app startup; health check fails so ECS restarts task |
   508→   508→| Saga step failure mid-transfer | Automatic compensating transaction (reverse debit), transaction marked `failed`, `transaction.failed` event published |
   509→   509→| External mock payment API timeout | Retry x3 with exponential backoff, then mark `payment.failed`, notify user |
   510→   510→| SES send failure | Log + retry once; never block the originating request |
   511→   511→| Event outbox processing failure | Increment `attempts`, retry with backoff up to 5x, then mark `failed` for manual/admin inspection |
   512→   512→| Unhandled exception | Global error middleware → 500 generic message, full detail only in server logs |

   516→   516→## 11. Non-Functional Requirements (practical targets)
   517→   517→
   518→   518→- Performance: p95 < 500ms for account/transaction endpoints under light demo load (<50 concurrent users).
   519→   519→- Reliability: single-AZ acceptable for a demo; stateless app tier allows redeploy/restart without data loss (state lives in RDS).
   520→   520→- Scalability: not a target for this build; document notes ECS Fargate can scale to N tasks behind ALB if ever needed.
   521→   521→- Availability: best-effort (no SLA); acceptable downtime for redeploys.
   522→   522→- Maintainability: modular monolith with clear module boundaries (Section 5) enables future extraction into real microservices without a rewrite.

   526→   526→## 12. Architecture Decisions (ADR summary)
   527→   527→
   528→   528→| Decision | Choice | Reason | Alternative | Tradeoff |
   529→   529→|---|---|---|---|---|
   530→   530→| Compute topology | Modular monolith, not microservices | Report's requirements are logically satisfied; K8s/microservices cost/complexity unjustified at this scale | True microservices on EKS | Harder to independently scale/deploy modules later, acceptable for demo |
   531→   531→| Event bus | Postgres outbox + in-process pub/sub | Achieves decoupling/replay without Kafka/MSK cost (~$50+/mo minimum for MSK) | Kafka/MSK, SNS+SQS | Lower throughput ceiling — irrelevant at demo scale |
   532→   532→| Database | Single Postgres, module-owned tables | ACID needed for money; avoids polyglot-persistence ops overhead | DynamoDB, per-service DBs | Slight coupling risk if module boundaries aren't respected in code |
   533→   533→| Fraud detection | Deterministic rules | Report explicitly permits this when sufficient; no training data exists for a real model anyway | Trained ML model | Less sophisticated detection — acceptable, documented as future work |
   534→   534→| Compute hosting | ECS Fargate (recommended) or single EC2 (cheapest) | Balance of low ops burden vs. absolute minimum cost — see Doc 3 cost comparison | EKS | EKS control plane alone costs $73/mo — rejected outright |
   535→   535→| Frontend hosting | S3 + CloudFront | Static SPA, cheapest possible with HTTPS/CDN | Amplify Hosting, EC2 | Amplify is also viable/similarly cheap; S3+CF chosen for explicit cost visibility |
